# 工程生成提示词

本目录保存可复用的工程生成契约和已填写参数的实例化版本（不代表生成工程已通过完整验收）。提示词描述的不只是功能范围，也包括安全、测试、部署、跨平台启动和验收要求。

## 文件职责

- `rebuild-rbac-system-v1.md`：权威通用模板。新增或修正规则时优先修改此文件。
- `rebuild-rbac_sys-system-v1.md`：以 `rbac_sys` 参数实例化的参考版本，用于生成当前工程和核对模板展开结果。

两份文件当前均为 v1.17。实例化文件不能反向成为另一套独立规范；通用要求发生变化时，应同步更新模板、实例和版本记录。

## 使用流程

1. 复制通用模板，并完整填写 `template_inputs`，不得猜测工程名、namespace、hostname 或端口。
2. 仅替换已定义的模板参数值，保留参数名称；实例文件只保留一个完整输入块，同时保留模板规定的派生关系和九端口登记。
3. 使用 Context7 核对会随版本变化的框架和工具用法；不可用时记录原因并改查官方文档。
4. 检查生成物中没有残留占位符、示例工程名、未登记端口或跨工程资源名。
5. 同步更新变更记录，并验证 Markdown 代码围栏、UTF-8 编码和安全约束。

提示词、README 和示例配置只能记录凭据变量名、来源与安全取值方法，禁止写入真实密码、token、私钥或完整含凭据连接串。

v1.14 修正临时文件权限与秘密传递，明确测试隔离、根 workspace 命令、代理信任、容器重建/健康检查和分阶段验证证据。官方资料及 Context7 核对范围见两份文档第 18 节。

修改后必须按输入块展开通用模板，与实例全文比较（仅标题和实例说明允许不同），同时检查版本、代码围栏和新增测试编号。实现状态与提示词版本分别维护；已有工程的未实现项不得通过降低模板要求消除。

## 容器生成的确定性

v1.15 第 14 节固定服务用途、场景、数量、profile 和清理边界：默认完整开发 7 个，按需加测试数据库和 RedisInsight 后为 9 个；完整 E2E 有独立测试服务，单机生产另有明确基线。九个端口输入不代表九个默认常驻容器。生成工程必须交付 `docs/container-topology.md`、`deploy/service-topology.json`、对应启动入口及 DEP-021～023 验收，禁止自行试建额外长期服务。

这是后续生成/整改的目标契约，不表示当前工程已经实现按需启动或独立 E2E 拓扑。修改提示词不自动改变已有 Compose 配置或运行中的容器；已有实现差距继续由 `docs/implementation-status.md` 跟踪。

## 首次启动的本机证书信任

v1.16 第 14 节新增本机 CA 信任与 Certificate Error 应对，第 15 节启动顺序同步引用。生成工程必须显式完成 CA 身份核对、宿主机信任安装、证书部署及实际浏览器验证，并提供跨平台排障/撤销说明；仅有证书文件、健康容器或通过容器 E2E 均不代表本机浏览器就绪。DEP-024～025 覆盖缺失信任、安装失败、身份不匹配及轮换。此修订只更新生成契约，不表示已经修改当前机器的信任库。

## 模板独立使用与最小提交

v1.17 修正测试配置归属、生产内部服务边界及完整后端测试准备流程。使用通用模板只需提供完整输入块；实例文档已内嵌全部参数，不依赖仓库根目录的 `project-identity.json`。文中要求的实现状态、toolchain、部署文件和验证报告均为生成工程的交付物，不是使用模板前必须存在的文件；历史实例经验需在新环境重新验证。

最小模板提交包含本目录三份 Markdown；同时保存仓库忽略规则时加根 `.gitignore`，共四个文件。工程源码、部署实现、lockfile 和实例运行报告另行提交。模板与实例一致性检查应直接读取实例的唯一输入块，不依赖未提交的工程文件。此模板版本不代表已有工程完成了新要求。
